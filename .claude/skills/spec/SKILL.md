## 目的

PLAN.md の「なぜ・何を作りたいか」を、AIが実装可能な仕様（SPEC.md）に落とす。
壁打ちで認識齟齬をなくし、思考を揮発させずにファイルに定着させる。

## いつ使うか

- **初期**: `/init` 完了後、最初の `/start` の前
- **フェーズ遷移時**: MVP→α→β等、スコープが変わるとき
- **新機能追加時**: SPEC.md にまだ書かれていない機能に着手するとき
- `/start` から誘導された場合

## 手順

### 1. 現状把握

以下を読み込む:
- **PLAN.md**: ビジョン、現在のフェーズ、直近の方向性
- **SPEC.md**: 既存の仕様（空テンプレートか、既に記述があるか）
- **understanding-map.md**: あれば、現在のアーキテクチャ把握状況
- **KNOWLEDGE.md**: あれば、関連する既知の制約・ハマり事例

### 2. スコープの確認

**引数がある場合**: その機能/フェーズに絞って仕様化する。
**引数がない場合**: PLAN.md の内容から仕様化すべき範囲を提案する。

```
📋 SPEC.md の現状:
- ビジネス要件: {記述あり/空}
- 機能仕様: {N件定義済み / 空}

PLAN.md の方向性から、以下を仕様化するのが良さそうです:
1. {機能候補A} — {理由}
2. {機能候補B} — {理由}

どの範囲で進めますか？（番号 or 自由入力）
```

### 3. 壁打ちで仕様を引き出す

ユーザーとの対話で仕様を具体化する。一度に全部聞かず、1-2問ずつ進める。

**ビジネス要件が空の場合（初回）:**
- ターゲットユーザーは誰か？（具体的なペルソナ）
- 既存の代替手段は何か？なぜそれでは不十分か？
- 最低限「これが動けばOK」と言えるものは何か？

**機能仕様を詰める場合:**
- ユーザーが何をしたら何が起きるか？（振る舞い）
- 完了の定義は？（受け入れ条件）
- エッジケースや制約は？

**壁打ちのルール:**
- ユーザーの回答が曖昧でもまず構造化して返す。「こういう理解で合ってる？」形式
- 完璧を求めない。80%の精度で書いて、実装中に `/learn` で更新するほうが良い
- ユーザーが「もういい」と言ったらそこで止める

### 4. SPEC.md に書き込む

壁打ちの結果を SPEC.md のフォーマットに沿って構造化する。

**書き込み前に必ずユーザーに提示して確認を得る。**

```
📝 SPEC.md に以下を追記します:

## ビジネス要件
### ターゲットユーザー
{内容}
### 提供価値
{内容}
...

## 機能仕様
### {機能名}
**目的**: ...
**振る舞い**: ...
**受け入れ条件**:
- [ ] ...
**制約・注意点**: ...

この内容でOK？修正があれば教えてください。
```

承認を得てから SPEC.md を編集する。

### 5. 既存セクションの更新（フェーズ遷移時）

SPEC.md に既に記述がある場合:
- 新しい機能仕様はセクションを追加する
- 既存の機能仕様の変更は差分を明示する
- 削除・変更の場合は理由をコメントで残す

### 6. 完了報告

```
✅ SPEC.md 更新完了

{追加/更新した内容のサマリ}

次のステップ:
- /start でIssueを作成して実装に入れます
- 実装中に仕様変更が必要になったら /spec {機能名} で更新できます
```

## 注意

- SPEC.md はAIとの認識齟齬をなくすためのもの。人間が読む設計書ではない
- 完璧な仕様を目指さない。実装を始められる程度に具体化すれば十分
- データモデル・API設計は、機能仕様が固まった後に必要に応じて書く
- PLAN.md は変更しない。PLAN.md の方向性を SPEC.md に具体化するだけ
