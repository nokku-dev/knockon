# knockon テンプレート／モジュール設計 SPEC

> 関連: Issue #62。本ドキュメントは #62 の方針コメントを正式 SPEC 化したもの。
> 由来: Claude.ai 設計セッション → design-session 配布（決定事項）。判断ログは Notion 思考ノートを参照。

## 1. 目的

テンプレートの価値は「網羅性」と「エビデンスに基づく設計」で担保する。「テンプレを足す」ではなく、評価フレームを定義し、実利用チェーンの export を生存検証済みの種として監査・補充する。

## 2. コアモデル

- 達成単位: 1アクション = 1タップ（既存）
- 採用単位: **モジュール**（3〜6リンク・1下位ゴール・自己完結。3〜6は厳格ルールでなくガイドライン）
- 階層: 扉 → 束 → モジュール → リンク
- 全階層を貫く単一モデル: **「採用時に ON な既定集合 ＋ 全要素トグル可」**
  - 束レベル: スターターモジュール（既定 ON）／追加おすすめモジュール（既定 OFF）
  - モジュールレベル: デフォルト ON リンク／追加リンク
- 「必須」等の permission 語は使わない。すべて state（既定 ON/OFF）で表現する。

## 3. データモデル

- `module { id, name, color, moment: [朝|昼|夜...], goal: [運動|スキンケア|家事|内省|食事...], source: official|user, kind: normal|custom }`
- `link { id, title, moduleId, default_on: bool, position: number, source: official|user, timerSeconds? }`
- 不変条件: どのリンクも必ず 1 モジュールに属す（official / user / 単一の「カスタム」インボックス）。module 無しの orphan は存在しない。
- リンクは「所属モジュール（論理クラスタ）」と「チェーン位置（物理順）」を独立に持つ。同一モジュールのリンクはチェーン上で非連続でよい。
- アンカーの出口（例: 仕事開始 / 就寝）は終端マーカーで、モジュール外。

## 4. discovery（テンプレ発見）

索引（扉2枚＋おまかせ）→ 束プレビュー → 採用確認 → マイチェーン

- 状態ゴール扉（既定・主導線）: 「いつを良くしたい?」→ moment（朝/夜）。おまかせ寄りのオピニオネイテッドな既定束。
- 成果ゴール扉: 「何を達成したい?」→ goal で横断フィルタ。
- おまかせ/人気: 目的の無い人向けの底。
- 両扉は同一カタログを moment / goal で切るだけ（状態扉＝1アンカー縦／成果扉＝複数アンカー横断）。
- 束プレビュー: 完成形（全モジュール）を見せつつ、スターターを前面・追加は折りたたみ。採用で入るのは **スターター × デフォルト ON リンクのみ**。
- モジュール詳細: 別画面を作らず束プレビュー内インライン展開（アコーディオン・同時1件・コンパクト）。
- 採用確認: position に基づき整列したチェーンをプレビュー。採用時の並べ替えはさせない（自動整列のみ）。

## 5. onboarding（初回ルート）

状態ゴール扉だけを通る、1画面1決定の連続:

1. Welcome（1行・カルーセル無し）
2. 最初のモーメント（朝/夜）
3. アンカー時刻
4. スタータープレビュー →「これで始める」
5. もう一方も?（opt-in 継続。floor は1チェーン）
6. 通知許可（投資後・理由付き、1回で両チェーン分）
7. 完了 ＋「✓ 明日◯時に起動」＋ [今すぐ1回試す]

- load-bearing: **アンカー時刻設定** と **通知許可**。どちらか欠けるとチェーンが発火せず初日に死ぬ。
- 進捗インジケータ・各画面の戻る導線・moment 選択の実分岐（夜→夜の束）は実装済み（#72 / [ADR-0031](decisions/0031-onboarding-first-run-route.md)）。
- 実装メモ（#72）: 1 本目は時刻アンカー付きで採用、2 本目（もう一方の moment）はデフォルト時刻で採用し調整はチェーン編集に委ねる（floor は 1 本）。初回判定は `app_settings.onboarding_completed`（新規=false→onboarding、既存ユーザーは migration で true）。

## 6. 編集UI（チップあり2層）

- 構造: 上＝チップ層（モジュール操作）／下＝リンクのフラットリスト（リンク操作）。
- チップ層: 採用中モジュールを色付きチップで一覧（ロスター）。**チップタップ＝ハイライト/絞り込みが主、外すは二次アクション**（破壊操作を既定にしない）。「＋追加」もここ。
- リスト層:
  - 並べ替え: グリップ起点のドラッグ（フラットリスト。ネスト DnD 不要）。
  - モジュールラベル: C 案＝左カラーストライプ ＋ run 先頭だけ名前（散らばると全行に名前が戻り自己修復）。
  - ON/OFF: 行トグル＝「一時停止」（チェーンから外すが残す）。
  - 削除: **編集モードの明示ボタンを主、左スワイプを従**。`source` でラベルが変わる:
    - user（カスタム/ユーザー追加）→「削除」（破壊的・アンドゥ付き）
    - official →「チェーンから外す」（非破壊・再追加可）
  - 消す系は「停止(OFF)」と「削除/外す」の2系統に整理する。
- カスタム追加: 「＋追加」→ アクションを「既存モジュール」か「カスタム」に振り分け。どちらでも module 所属（新要素クラスを増やさない）。
- カスタム: 単一の中立グレー・インボックス（未整理）。複数選択 → 命名＋色付けで **ユーザーモジュールに昇格**（昇格後は公式と同列・複数可）。インボックス自体は常に単数（graft の Dump→整理と同型）。
- アンドゥ: 削除/外す/モジュール一括外しに対応。

> 実装メモ（#73 / [ADR-0032](decisions/0032-edit-ui-two-layer-chips.md)）: コア機能（並べ替え・ON/OFF 一時停止・source 別削除・カスタム追加）を実装。ON/OFF は `nodes.active` で表現（停止は Today から外すが残す・非破壊）。「+追加」ノードは固定の custom inbox モジュール（`mod-custom-inbox` / kind='custom'）所属。C 案ラベルは `computeRunLeaders` で run 先頭のみ名前表示。
>
> 実装メモ（#95）: **チップタップ＝絞り込み**（再タップ解除・絞り込み中は並び替え無効＝部分集合 index と全体 order_index 不一致のため）と**「+追加」の振り分けピッカー**（ロスター + custom inbox から所属先選択・既定 custom inbox）を実装。
>
> 実装メモ（#93）: **カスタム→ユーザーモジュール昇格**。custom inbox ノードを複数選択 → 命名 + 色付け（`PROMOTE_COLORS`）で user モジュール（kind='normal' / source='user'）を生成し、選択ノードの module_id を付替え。モジュールは即 DB INSERT（FK + チップ表示のため）、ノード付替えは保存で永続化（既存ノードは `updateNodeModule`）。昇格後に保存せずキャンセルするとモジュール行が orphan として残るが、ノード未参照なのでロスター非表示・実害なし（Phase 1 受容）。
>
> 実装メモ（#94）: **一括外し**（絞り込み中のモジュールを「まとめて外す」二次アクション）と **undo**（削除/外し/一括外しを直近 1 件・5 秒以内に取り消し、position/所属/active を復元）を実装。方針は §8 参照。
>
> **後送り**: 空状態（#74）。

## 7. アクセシビリティ要件

- モジュールは色のみに依存しない（色覚特性で teal/gray が潰れる）。非色キュー（ラベル常時 or アイコン/形）を併用。
- タッチターゲット ≥ 44px。トグル/スワイプに明示ボタンの代替を用意。
- 補助テキスト（faint グレー）は WCAG AA を満たすコントラストに。

## 8. 未解決（実装前に要定義）

- ~~通知拒否時のフォールバック（アプリ内アラーム / 手動起動）~~ → **解決済み（#72 / [ADR-0031](decisions/0031-onboarding-first-run-route.md)）**: Today 常時表示をフォールバックとする（[ADR-0020](decisions/0020-deprecate-manual-firing-concept.md)）。通知拒否時は「通知が無くても Today を開けば実行できる」と明示するだけ。新規アラーム機構は作らない。
- 空状態（全 OFF 時 / モジュール全削除時） → #74 で扱う（編集UI 本体は未対応）
- ~~アンドゥの多重・タイムアウト方針~~ → **解決済み（#94）**: **多重 = 直近 1 操作のみ**（新しい削除/外し/一括外しで undo 対象は上書き）。**タイムアウト = 5 秒**（`UNDO_TIMEOUT_MS`、経過で削除確定＝undo 不可）。undo 対象は削除/外し/一括外しの 3 種で、元の position・所属（module_id）・active を復元する（`reinsertByIndex`）。編集はそもそも保存前ならキャンセルで全て破棄でき、undo はそれより手前の即時取り消し導線。
