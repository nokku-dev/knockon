# knockon テンプレ監査 — 評価軸と F1-F6

> 起点: Issue #121 / [docs/template-modules-spec.md](template-modules-spec.md) §9 v0 モジュールカタログ。
> 位置づけ: 「テンプレを足す / 充実させる」を曖昧完了タスクにしないための評価フレーム ([KNOWLEDGE.md K-029](../KNOWLEDGE.md#k-029)) + 初回監査ログ。
> 評価軸 = 完了条件: 新規モジュールの追加 / 既存の改廃は本ドキュメントの 3 軸照合に通すこと。

## 1. 目的

K-029 の教訓に従い、「テンプレを足す」前に評価フレームを 1 枚で言語化する。具体的には:

- **網羅性 × エビデンス可視性 × 一意性** の 3 軸で v0 カタログ ([catalogSeed.ts](../src/catalogSeed.ts) / SPEC §9) を監査する。
- 監査結果 (F1-F6) を**今後の補充 / 改廃の照合表**として残す。
- 同型の判断 (= モジュール追加 / 統合 / 廃止) を再度議論しないために、軸と結論をここに固定する。

副次効果として、新規ユーザーが採用時に見る「テンプレ群」の品質保証 (= 実需に紐付いている / 排他的 / カバレッジ既知) を内部で説明できる状態にする。

## 2. 評価軸 (3 つ)

| 軸 | 定義 | 不合格シグナル |
|---|---|---|
| **一意性** | 各モジュールの存在意義が他と排他で、ユーザー視点で「どっち?」の選択コストが小さい | 同 moment × 同 goal で内容が被る / 1 モジュール内のリンクが他モジュールと半数以上重複 |
| **エビデンス可視性** | そのモジュールが「実 export 由来 (= 自分の生存検証済みの種)」か「汎用化 (= 仮説)」かが追跡できる | 出典が冒頭の散文にだけ書かれていて個別モジュールに紐付かない / 採用率 0 のモジュールが残る |
| **網羅性** | 4 アンカー (起床 / ランチ / ディナー / 就寝) × goal カテゴリ (health / skincare / exercise / beverage / meal / grooming / chores / reflection) の組み合わせで、実需のあるマスがカバーされている | アンカー間で密度が極端に偏る / goal × moment マトリクスに「常に欲しいが空欄」の組み合わせが残る |

### 軸間の優先順位

「網羅性 < エビデンス可視性」: 網羅性ギャップを埋めるためにエビデンスの無いモジュールを汎用追加するのは **やらない**。空欄は空欄のまま残し、実 export の蓄積か明示的な仮説検証で埋める ([K-031 最小核](../KNOWLEDGE.md#k-031))。

「一意性 ≧ 網羅性」: 一意性が崩れた状態で網羅性を上げると、採用 UI で「どれを選べばいいか分からない」状態を生む。一意性は補充より優先。

## 3. 監査スコープ

- 対象: v0 catalog ([catalogSeed.ts](../src/catalogSeed.ts) `V0_CATALOG_DEFS` 14 モジュール + custom inbox 1)。SPEC §9 と 1-1。
- 対象外: custom inbox (`mod-custom-inbox`) は編集 UI の受け皿で discovery には出ないため対象外 ([ADR-0030](decisions/0030-template-module-link-data-model.md))。
- アンカー: 朝 (起床) / 昼 (ランチ) / 夜 (ディナー / 就寝) の 4 枠。

### 現状サマリ (件数)

| アンカー | モジュール数 | starter 数 | 採用候補 (●defaultOn link) | 追加候補 (○) |
|---|---|---|---|---|
| 朝 (起床) | 9 | 4 | 18 | 6 |
| 昼 (ランチ) | 1 | 1 | 3 | 0 |
| 夜 (ディナー) | 1 | 1 | 2 | 1 |
| 夜 (就寝) | 3 | 2 | 9 | 3 |

朝に密度が集中し、昼 / 夜ディナーが薄い構造。これが網羅性 F4 / F5 の前提。

## 4. 監査結果 (F1-F6)

各 finding は **軸 / 該当 / 観察 / 対処** の順で記す。 ◎=合格 / ●=対応必要 / △=要観察 / ×=不合格 で軸ごとの当否を併記。

### F1: 食事系 3 モジュールは moment 軸で排他されている (一意性 ◎)

- **該当**: `mod-breakfast` (朝 / meal / ★) / `mod-lunch` (昼 / meal / ★) / `mod-dinner` (夜ディナー / meal / ★)
- **観察**: 同 goal だが moment が直交。採用 UI (= 状態ゴール扉) では moment 選択が先行するので、同時に 2 つ並ぶことが無い。一意性 OK。
- **対処**: **現状維持**。今後 meal 系を追加するときも moment 排他を守る (= 同 moment に 2 つ目の meal モジュールを足さない)。

### F2: 朝 `exercise` 2 モジュールの選択コスト (一意性 △)

- **該当**: `mod-cardio` (有酸素) / `mod-strength` (筋トレ・補給) はいずれも moment=朝 / goal=exercise / starter=false。
- **観察**: 内容は異なる (有酸素 vs 筋力) が、ユーザーから見ると「朝の運動どっち?」の選択コストが発生する。両方追加するのは過剰、片方だけなら自分の運動スタイル次第。成果ゴール扉で goal=exercise を選んだとき両方プレビューされる構造 (SPEC §4 「成果扉=複数アンカー横断」) なので、 仕様通りではある。
- **対処**: **現状維持** (両立は許容)。 ただし discovery #71 の prepare/採用 UI で両者の差分 (有酸素 vs 筋力) を 1 行で説明する短文を将来検討。 今 issue では追加しない。

### F3: モジュール個別の出典 (export 由来 / 汎用化) が機械的に追跡できない (エビデンス可視性 ●)

- **該当**: 全 14 モジュール。
- **観察**: SPEC §9 冒頭で「実 export 由来 + 汎用化」と書かれているが、 `CatalogModuleDef` (catalogSeed.ts) に `evidence` フィールドが無く、 どのモジュールが「自分の生存検証済みの種」 ([K-031](../KNOWLEDGE.md#k-031)) で、 どれが汎用化されたかが個別に辿れない。補充候補との出自比較ができない。
- **対処**: **本監査ログでの分類で代替** (下記表)。 将来 `CatalogModuleDef.evidence: 'export' | 'generalized'` を追加する余地はあるが、 v0 範囲では別 Issue 化せずバックログ。

#### 出典分類 (本監査ログでの推定)

| モジュール | 出典推定 | 根拠 |
|---|---|---|
| mod-wake-water / mod-morning-skincare / mod-breakfast / mod-day-planning / mod-lunch / mod-dinner / mod-bath / mod-evening-reflection | **export 由来** (= 自分の運用にある起床〜就寝のスターター枠) | starter=true / 自分の固定ルーティン |
| mod-cardio / mod-strength / mod-coffee / mod-grooming / mod-morning-chores / mod-night-chores | **汎用化** | starter=false の "追加おすすめ"。 一般化された候補 |

> この分類はあくまで監査時点の推定。 将来 export 由来かどうかを別軸で持ちたくなったら `evidence` フィールドを足す ([K-030 state vs permission](../KNOWLEDGE.md#k-030) と同型: 分類軸を独立に持つ)。

### F4: 昼アンカーが 1 モジュールのみ (網羅性 △)

- **該当**: `mod-lunch` のみ。 採用候補 3 link。
- **観察**: 昼休憩の運動 / 内省 / メール処理など、実運用で起きうる行動が無い。 ただし K-031 (最小核) と「網羅性 < エビデンス可視性」のルール (§2) から、 自分の export に無いものを汎用追加するのは取らない。
- **対処**: **空欄維持**。 補充は実 export の蓄積を待つ。 補充候補は §5 ギャップ表に記録。

### F5: 夜就寝アンカーに `exercise` / `beverage` モジュールが無い (網羅性 △)

- **該当**: 夜就寝の 3 モジュール (家事 / 入浴 / 内省) は chores / skincare / reflection のみ。
- **観察**: 寝る前のストレッチは `lnk-stretch-night` (defaultOn=false) として `mod-evening-reflection` 内に潜っているが、 モジュールレベルでは exercise 枠が立っていない。 ハーブティー / 白湯等の beverage も同じく無し。
- **対処**: **空欄維持** (F4 と同方針)。 stretch がリンク粒度で既に居場所を持っているため、 独立 exercise モジュール化の必要性は低い。 beverage も同様。

### F6: 「コーヒー」モジュールが 1 リンクで、 隣接 meal モジュールとの粒度差 (一意性 △ / エビデンス ●)

- **該当**: `mod-coffee` = `lnk-brew-coffee` 1 本のみ。 朝アンカー / goal=beverage / starter=false。
- **観察**: 単独 1 リンクモジュールは採用 UI で「これ何のモジュール?」と読みづらい (粒度ばらつき)。 ただし「コーヒー」は実運用で固有の儀式性を持つ可能性が高く ([F3 分類](#f3) では汎用化に倒したが export 由来寄りの可能性もある)、 朝食モジュールに統合するとモジュールの存在意義 (= 同じ目的のリンクを束ねる単位) が崩れる。
- **対処**: **現状維持**。 採用後に編集 UI でユーザーが朝食モジュールへ統合したくなった場合は §6 編集 UI のモジュール所属付替え (`updateNodeModule` / [#93 昇格](../KNOWLEDGE.md)) で対応可能なため、 テンプレ側で先回りした統合はしない。 単独モジュールの粒度ばらつきは「素のまま見せる」方針で許容する。

## 5. 網羅性ギャップ表 (補充候補バックログ)

評価軸「網羅性 < エビデンス可視性」 (§2) に従い、 **空欄を埋めるためだけのモジュール追加は採用しない**。 補充候補は将来の export 蓄積で実需が見えたタイミングで照合する種リスト。

| アンカー | 候補 | 想定 goal | 想定 starter | 補充判断のトリガー |
|---|---|---|---|---|
| 昼 (ランチ) | 昼散歩 | exercise | ○ | 自分の昼休憩運用に「散歩」が定着 |
| 昼 (ランチ) | 短い内省 (5 分ノート等) | reflection | ○ | 同上、 内省で |
| 夜 (就寝) | 寝る前 stretch (独立モジュール化) | exercise | ○ | F5 の link 粒度から独立化したい強い理由が出たとき |
| 夜 (就寝) | 寝る前 beverage (ハーブティー / 白湯) | beverage | ○ | export に定着 |
| 朝 (起床) | 朝の bevarage (お茶 / 緑茶) | beverage | ○ | コーヒー以外の朝飲料の定着 |

> 上記候補は補充候補であって採用予定ではない。 採用するときは本 audit に F# を追加して評価軸照合の記録を残す。

## 6. 更新ルール

- 新規モジュール追加時: §2 の 3 軸で当否を判断し、 F# を本ドキュメントに追加する。
- 既存モジュール改廃時: 該当 F# を更新し、 改廃理由を 1 行で残す。
- 評価軸自体の更新: SPEC §9 / catalogSeed.ts / 本ドキュメントを同時に更新 ([.claude/rules/spec-sync.md](../.claude/rules/spec-sync.md))。
- 軸の追加 / 削除は ADR を起票する (= 評価軸の変更は重い判断)。
