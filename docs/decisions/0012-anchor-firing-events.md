# アンカー発火イベントを「1 日 1 回の不可逆事実」として正準データに追加する（時刻/場所共通）

## 文脈

Phase 1.5 で時刻アンカー、Phase 1.6 で場所アンカーの発火状態を Today で表示する仕組みを導入した。当初の設計:

- **時刻アンカー (PR-1.5)**: 現在時刻 ≥ `anchor.time` の動的派生で発火状態判定
- **場所アンカー (PR-1.6 初期実装)**: focus 復帰のたびに GPS を取得して距離計算

実機検証中に 2 つの問題が顕在化した:

1. **UX 問題**: 場所アンカーで毎 focus に GPS を取り直すと Today のローディングが 20-30 秒 block (PR-1.6 で非同期化により解消) + そもそも「毎回再判定」がユーザーのメンタルモデルと合わない。
2. **概念整合性**: ユーザーが意図したのは「**その場所に行った時点でそのチェーンが一通り行われるトリガーが発火**」というイベント概念。一度発火したら範囲を出ても「今日はもう発火した」扱いが直感的。動的派生だと範囲を出るとピルが消える挙動になり [CLAUDE.md](../../CLAUDE.md) §Augmentation原則「マイナスを指差さない」と微妙に逆向き (離脱を指差すビジュアル)。

時刻アンカーと場所アンカーで発火モデルが揃っていない (時刻は一方向の動的派生 / 場所は双方向) のも、Phase 2 で発火履歴を可視化する際に二重の派生関数を維持するコストになる。

[ADR-0001](./0001-chain-data-model.md) §決定4 で「永続化される正準データは `(ノード, 日付, bool)` のみ」と書いていたが、これは **ノード達成側の話**。アンカー発火はノード達成とは別軸の事実なので、別 ADR として正準データのスコープを拡張する判断を立てる。

## 検討した選択肢

- **案A（採用）**: アンカー発火を「観測した不可逆イベント」として正準データに追加。新規テーブル `anchor_firings (anchor_id, date)` を作る。**時刻/場所共通の 1 回発火モデル**。発火検出は focus 復帰時のポーリング、発火後はその日中 DB record があるだけで発火中扱い。GPS / 時刻判定は不要。
- **案B（却下）**: 場所のみ 1 回発火モデル、時刻は現状の動的派生のまま。整合性が崩れる + Phase 2 で発火履歴を扱うとき二重実装になる。
- **案C（却下）**: 動的派生を全部維持。GPS 毎 focus 問題は非同期化で緩和できるが、ユーザーのメンタルモデルと合わない (発火イベントが事実として残らない)。

## 決定

案A を採用する。具体的に以下を固定する:

1. **新規テーブル `anchor_firings`**:
   - カラム: `anchor_id TEXT`, `date TEXT`
   - `PRIMARY KEY (anchor_id, date)` で 1 日 1 回の発火イベントのみ
   - `anchor_id` は `anchors(id)` への外部参照
2. **アンカー発火イベントを正準データに追加**。本 ADR は [ADR-0001](./0001-chain-data-model.md) §決定4 の「正準データは `(ノード, 日付, bool)` のみ」を以下のように再解釈する:
   - **ノード達成**: `(node_id, date, achieved)` のみ — これは ADR-0001 で確定済み、変更なし
   - **アンカー発火**: `(anchor_id, date)` を新規追加 — 本 ADR で確定
   - **両者は別軸の事実** であり、達成率・連鎖の流れ・定着判定・星種別などの派生値は引き続き保存しない
3. **派生関数**: `isAnchorFiringToday(firings, anchor_id, date): boolean` を domain 層に追加。発火 record があれば true。
4. **検出ロジック (useTodayData)**:
   - 時刻アンカー: focus 復帰時に「今日まだ発火していない」かつ `isTimeAnchorFiringNow(anchor, now)` が true なら発火 record を INSERT
   - 場所アンカー: focus 復帰時に「今日まだ発火していない」場合のみ GPS を取得 → 範囲内なら発火 record を INSERT
   - 発火後は GPS / 時刻判定とも不要 (DB record があるだけで発火中扱い)
5. **アンカー編集時の発火 record の扱い**: 編集しても **今日の発火 record は変更しない**。今日発生した事実として残す。新 anchor 設定は次の発火タイミングから適用。
6. これは v1 確定事項。覆す場合は本 ADR を `superseded` にする新規 ADR が必要。

## 理由

- **ユーザーメンタルモデル整合**: 「トリガーが発火 = チェーンが一通り発生する起点」は不可逆イベント。範囲を出ても「今日はもう発火した」扱いが直感的。時刻も「その時刻に達した瞬間に発火」のイベント。
- **Augmentation原則との整合**: 動的派生だと「範囲を出る / 時刻を巻き戻る」でピルが消える。ユーザーから見ると「離脱を指差す」逆向きのビジュアル。1 回発火モデルなら一度発火した「祝福」がその日続く ([CLAUDE.md](../../CLAUDE.md) §Augmentation原則 / [DESIGN-SYSTEM.md](../../DESIGN-SYSTEM.md) §0 Celebrate 主)。
- **「保存は事実、解釈は関数」の精神 ([ADR-0001](./0001-chain-data-model.md))**: アンカー発火は **観測した事実** (派生値ではない)。同 ADR の「派生値 / キャッシュ / 非正規化」禁止の対象ではない。むしろ事実保存の原則に正面から沿う。
- **GPS / 時刻判定の再計算頻度を最小化**: 一度発火後はチェック不要 → UX 改善 (PR-1.6 で踏んだ毎 focus GPS block 問題の構造的解決)。
- **時刻/場所で同じデータパス**: 一貫性。Phase 2 で発火履歴可視化するときも単一データソース。
- **案B を却下する理由**: 時刻と場所で発火モデルが違うと、ユーザー説明・実装メンテ・Phase 2 派生関数すべてで二重コストが発生する。
- **案C を却下する理由**: 「事実を残さない動的派生」のままだと、Phase 2 で「過去 14 日間でこのチェーンは何日発火したか」のような派生を実装できない (元事実が無いから)。

トレードオフ:
- [ADR-0001](./0001-chain-data-model.md) の「正準データは `(node_id, date, bool)` のみ」が文字通りでは成立しなくなる。本 ADR で「達成側は変えない、アンカー発火側は別軸」と明示し、K-005 双方向リンクで判断系譜を保つ (ADR-0001 §決定4 に逆参照を残す)。
- スキーマ変更 (新テーブル) のマイグレーションが必要。`CREATE TABLE IF NOT EXISTS` で冪等なので既存 dev DB は次回起動時に自動拡張。本番運用前なのでデータ移行は不要。
- 発火 record を編集中の anchor で「無効化しない」判断は、anchor を頻繁に切り替えるユースケースでは違和感が出る可能性。v1 はチェーン編集自体が無いので問題なし (Phase 2 で再評価)。
- アンカー削除時 / チェーン削除時 (Phase 2) に `anchor_firings` の orphan record をどう扱うかは Phase 2 の判断対象。

- **これは v1 の確定事項**。Phase 2/3 着手後にも再検討せず、覆す場合は新規 ADR が必要。

## 追補 (2026-08-16 / [ADR-0055](./0055-anchor-firing-source.md))

§決定1 のカラム定義を **`source TEXT NOT NULL` の追加で拡張**した（`'foreground'` | `'geofence'`）。
#301（Phase 1.6b）で OS ジオフェンスを実装した結果、発火を書く経路が 2 つ（前景の GPS 判定 /
region Enter）になり、**どちらが観測したかが記録に残らない**問題が実際の QA で 2 回顕在化したため。

⚠ 本 ADR は **supersede されていない**。核（1 日 1 回の不可逆な観測事実 /
`PRIMARY KEY (anchor_id, date)` / 派生値は保存しない）は変わらず、
「その事実を何が観測したか」を同じ行に持つだけ。詳細は [ADR-0055](./0055-anchor-firing-source.md)。
