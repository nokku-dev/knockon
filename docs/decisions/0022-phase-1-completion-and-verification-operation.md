# Phase 1 完成判定の達成と検証期間の運用方針 (ADR-0006 補完)

## 文脈

Phase 1 の実装が**全件 merged** された:

- **Phase 0**: データ層 (ADR-0001)、 ts-jest + better-sqlite3 (ADR-0008)、 expo-router (ADR-0011)
- **Phase 1.1〜1.4**: 実機到達、 ノード達成、 1 本スパイン (ADR-0009/0010)、 手動発火 (※後に [ADR-0020](0020-deprecate-manual-firing-concept.md) で「Today 全表示 + ノードタップ」と再定義)
- **Phase 1.5/1.6**: 時刻アンカー / 場所アンカー / アンカー発火イベント (ADR-0012)
- **Phase 1.5b**: Dev Client 移行 (ADR-0017)、 通知 (ADR-0019)、 通知タップ → ディープリンク + foreground Toast
- **Phase 1.7/1.8**: CRUD 前倒し (ADR-0014)、 schema migration (ADR-0016)、 削除 + FK CASCADE
- **Phase 1.7b**: DnD ライブラリ (ADR-0015 / K-019/K-020)
- **Phase 1.9**: 達成セレブレーション (ノック + マーカー + テキストバウンス)
- **Phase 2 前倒し**: variant 曜日マップ + active/stocked 切替 ([ADR-0018](0018-variant-phase-2-frontload.md))
- **PR-X**: Today マルチチェーン + Bottom Sheet ([ADR-0021](0021-today-multichain-bottom-sheet.md))
- **chore**: preview build 整備 (eas.json + CLAUDE.md)、 GitHub Actions CI

実装は揃ったので [ADR-0006](0006-phase1-completion-and-scope-narrowing.md) の早期検証ゲート、 つまり「**Today を実機で数日継続して回す**」フェーズに正式突入する。

ここで「検証中に並行して何を進めるか / 何を進めないか」 + 「Phase 2 着手のトリガー」を明示する必要がある (ADR-0006 を補完)。

## 検討した選択肢

- **案 A**: 検証中に Phase 2 設計を先に進める (サブチェーン / weekday-specific 通知 / background ジオフェンス等) — 検証結果を待たずに着手。 [K-001 (快適で得意な作業が実リスクに触れていない罠)](../../KNOWLEDGE.md) を踏むリスク。 ADR-0006 と矛盾。
- **案 B**: 検証中は何もしない (ADR-0006 純粋遵守) — シグナル収集に集中、 並行作業ゼロ。 検証時間が浪費される可能性。
- **案 C**: 検証に依存しない実用作業を並行 (CI / preview build / 純粋関数の hook テスト等) — 機能拡張は避け、 infra / 品質作業のみ。 Phase 2 着手は「不便驅動」(= 検証で具体的不便が観測されてから)。

## 決定

**案 C** を採用。 加えて以下を確定:

### 検証中に並行して進める実用作業 (= 機能拡張ではないもの)

- ✅ **preview build 整備** (本 ADR 着手前に PR #36 で完了)
- ✅ **GitHub Actions CI** (本 ADR 着手前に PR #37 で完了)
- ⏸ hook テスト追加 (useChainEdit / useTodayData) — 必要性が出てから
- ⏸ iOS Dev Build 整備 — Apple Developer Program 課金判断とセット、 後回し
- ⏸ アクセシビリティ監査 — 必要性が出てから

### 集めるシグナル (検証で観測したい 4 つ)

1. **「毎朝 Today を開く」が続くか** (= 通知動線が機能しているか、 Phase 1 完成判定の中核)
2. **variant null 日のグレー表示が UX として効いているか** (PR-1.9 後のユーザーフィードバックの正しさ検証)
3. **場所アンカー × background ジオフェンスの必要性** (Phase 1.6b 候補の判断材料)
4. **Bottom Sheet + ChainCard 一覧の UX 使いやすさ** (ADR-0021 メンタルモデルの正しさ検証)

### Phase 2 着手のトリガー

**「これがないと困る」シグナル (= 不便驅動)** で進める。 期間ベース (N 日連続使用) ではなく、 観測された具体的不便から逆算して着手する機能を決める。

例:
- 「通勤中に通知が来ても Today が見えない」 → Phase 1.6b (background ジオフェンス)
- 「曜日で違うサブ習慣を持ちたい」 → サブチェーン
- 「daily 1 通知だと曜日切替の情報が足りない」 → variant weekday-specific 通知
- 「シグナルなし」 → Phase 2 着手は保留、 検証継続

## 理由

- **ADR-0006 と整合**: 「設計の精密化より実機到達を優先」を運用フェーズで実装。 検証中は機能設計の手を止め、 実機シグナルだけを情報源にする。
- **K-001 罠回避**: 「快適で得意な作業 (= Phase 2 設計の前倒し)」に逃げないため、 並行作業のスコープを「機能拡張ではない infra / 品質」に限定する。 案 A は K-001 そのもの。
- **検証時間の有効活用**: 案 B (= 何もしない) は時間損失。 検証に依存しないものは並行で進めて infra を底上げ。 CI 整備は今後の Phase 2 着手時にも効く投資。
- **不便驅動の Phase 2 トリガー**: 「N 日連続使用」のような期間ベースは恣意的。 「これがないと困る」が出た時点で Phase 2 着手すれば、 機能の必要性が事前に検証されている (= K-001 罠の二重防止)。

## 想定される影響

### 即時の影響

- **検証期間中の判断軸が明確化**: 「これは検証結果に依存するか」を物差しに、 並行作業の可否を判断できる
- **Phase 2 着手の意思決定がインクリメンタルに**: 「Phase 2 全体を計画 → 着手」ではなく、 「観測された不便 1 つ → 対応する Phase 2 候補 1 つ」のフロー
- **ADR-0006 の運用フェーズが定義された**: ADR-0006 は「Phase 1 完成判定の基準」を書いたが、 本 ADR で「Phase 1 実装完了後の運用」を補う

### 将来の覆すコスト

- **「期間ベース判定 (N 日)」 への変更**: 検証で「不便驅動だと前進感が出ない」シグナルが出たら、 期間ベース (3 日 / 7 日) に切り替える別 ADR を作る判断ができる。 ただし K-001 罠は注意。
- **「Phase 1 出荷 (ストア配布) を先に」 への切替**: SPEC.md の完成判定は「N=1 実運用」だが、 検証で「もう他人にも配りたい」が出たら出荷準備に方針転換できる。 別 ADR で。
- **CI / preview build を撤回**: ほぼあり得ない。 今後の作業全部にプラスにしか働かない。

### 注意点

- **「不便驅動」は判断の遅延ではない**: 「不便が出ない = 待ち続ける」のではなく、 「不便が出ない = Phase 2 必要性が低い」と解釈する。 Phase 1 出荷判断 (= 他人に配る判断) に切り替える経路もある。
- **シグナル収集の媒体**: 直接アプリ内で記録する機能はない (Phase 1 範囲外)。 ユーザー (= 自分) が手元のメモ / Notion / 別ツールで観測を書き留め、 必要なら `/learn` / `/idea` で KNOWLEDGE / PLAN に蓄積。
