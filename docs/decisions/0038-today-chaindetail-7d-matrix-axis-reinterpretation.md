# Today ChainDetail ノード行の直近 7 日マトリクスを SPEC §3「v1 単一窓 14D 固定」の軸別再解釈として正式化する

## 文脈

Issue #125 で Today の Bottom Sheet 内 ChainDetail の各ノード行の右端に直近 7 日間 (7D) の達成グリフマトリクスを実装した (commit `be452be`)。実装そのものは UX 上の意図 (実行直前の行内で「次に何をするか」と「直近どこまで積めているか」を視線移動なしで把握できる) を満たしたが、SPEC §3「進捗の見せ方 (v1)」の以下の 2 文と字面が衝突する状態が残った:

- 「ウィンドウは **v1 は単一（14D 固定）**。7/14/31 切替は v1 非スコープ。」(§3 line 58)
- 「Today / チェーン詳細の窓は 14D を維持する。」(§3 line 58 末尾)

一方で同じ §3 line 60 では #125 の 7D マトリクスを存在として記述しており、SPEC 単体読みで矛盾する形になっていた。

これは [ADR-0037](./0037-analytics-date-matrix.md) (分析タブの 60D マトリクス) のときに踏んだ「禁止 UI を軸別に再解釈する」パターン ([K-015](../../KNOWLEDGE.md)) と同型: 「全称ルールを後から軸別に分離して両者を共存させる」。本 ADR でこの軸別再解釈を Today ChainDetail 7D マトリクスにも明示的に拡張し、SPEC §3 line 58 を「軸ごとに窓を持つ」表現に書き換えて矛盾を解消する。

## 検討した選択肢

- **案A (採用): 14D 固定ルールを「窓ごと」軸別再解釈し、7D / 14D / 60D の 3 窓を v1 で正式化する** — SPEC §3 line 58 の「14D 固定」と「7/14/31 切替は v1 非スコープ」を**目的別に窓を持つ**表現に書き換える。窓ごとに目的を明示:
  - 7D = Today ChainDetail ノード行 (実行直前の振り返り、固定・横スクロールなし)
  - 14D = Today カード / チェーン詳細の標準窓 (定着判定・スパイン伸び・KPI)
  - 60D = 分析タブのマトリクス (中期俯瞰、横スクロール)

  「ユーザーが窓を切り替える」ことは引き続き v1 非スコープ (= UI に窓選択チップを置かない)。窓の値は実装側の固定値として目的ごとに決まる。

- **案B (却下): SPEC §3 を supersede し「v1 単一窓」表現を全廃する** — 全廃は ADR-0037 の判断 (= 単一窓は基本ルールとして維持し、特定セクションだけ例外) を覆すことになる。K-015 「軸別再解釈は supersede しない部分変更」の精神に反する。

- **案C (却下): SPEC §3 line 58 を残したまま「実装と SPEC が矛盾するが受容」とコメントで明記する** — `.claude/rules/spec-sync.md` が明示的に禁止する運用 (= 実装と仕様の乖離放置)。次回ここを読む実装者 / レビュアーが必ず再議論することになるため、コスト的にも悪い。

## 決定

案A を採用する。

### 1. SPEC §3「進捗の見せ方 (v1)」line 58 の改訂

旧:
> ウィンドウは **v1 は単一（14D 固定）**。7/14/31 切替は v1 非スコープ。ただし**分析タブの達成マトリクスのみ 60 日窓（例外、#115 / ADR-0037）**。Today / チェーン詳細の窓は 14D を維持する。

新:
> ウィンドウは **目的ごとに窓を持つ (v1)**: **Today カード / チェーン詳細スパイン / 定着判定 = 14D** (標準窓)、**Today ChainDetail ノード行のミニマトリクス = 7D** (#125 / ADR-0038、 実行直前の振り返り)、**分析タブの達成マトリクス = 60D** (#115 / ADR-0037、 中期俯瞰)。**ユーザーが窓を切り替える UI (7/14/31 切替チップ等) は v1 非スコープ** — 窓の値は目的ごとに実装側の固定値として決まる。

### 2. SPEC §5「v1 非スコープ」line 72 の改訂

旧:
> **ウィンドウ 7/31 切替**（v1 は 14D 固定）。

新:
> **ユーザーが窓を切り替える UI** (Today / 分析の窓選択チップ等)。窓の値そのものは目的ごとに固定 (§3 参照)。

### 3. 軸別再解釈の確立

SPEC §3 line 58 の「v1 単一窓 14D 固定」全称ルールを、「**v1 では目的ごとに窓を 1 つだけ持つ (= 同じ目的に複数窓を持たない)**」と再解釈する。これは:

- ADR-0037 (分析タブ 60D) と本 ADR (Today ChainDetail 7D) を矛盾なく内包する
- 「目的が異なる窓は別軸として並存できるが、同じ目的に複数窓は持たない」境界線を残す (= 「Today カード」に 7D / 14D / 31D 切替を足す等は引き続き禁止)

### 4. 双方向リンク (K-005 ルール)

- 本 ADR が SPEC §3 / §5 / ADR-0037 を逆参照する
- 本 ADR を SPEC §3 / §5 / DESIGN-SYSTEM (該当箇所があれば) / ADR-0037 (関連節) から逆参照する

## 理由

- **SPEC 矛盾の解消**: line 58「14D 維持」と line 60「7D マトリクス」の同 §3 内字面衝突を、軸別再解釈で解消する。`.claude/rules/spec-sync.md`「実装と仕様の乖離は放置するほど埋めるコストが増える」と整合。
- **既存判断の保存 (K-015 同型)**: ADR-0037 の「単一窓は基本ルール / 特定セクションだけ例外」精神を維持。supersede ではなく部分変更 (= 全称ルールを軸別に分離) で済ませる。
- **境界線の明示**: 「窓を増やす」ことが青天井になるのを避けるため、「目的が異なる ⇒ 別窓 OK / 同じ目的に複数窓 ⇒ 切替 UI 禁止」を文字で残す。Phase 2 以降で「同じ目的で 7/14/31 切替を足したくなった」場合、ここを再議論するための呼び出し点になる。
- **K-015「全称禁則を後続 ADR で軸別に拡張するパターン」の 2 度目の適用**: 初回 (ADR-0037) は禁止 UI ルールの軸別再解釈、今回 (ADR-0038) は窓ルールの軸別再解釈。同じパターンが効くことを再確認し、運用テンプレとして KNOWLEDGE 側にも反映余地がある (今回は KNOWLEDGE 改訂は伴わず、ADR-0037 と本 ADR の 2 事例で十分とする)。

トレードオフ:
- **「v1 単一窓 14D 固定」の字面が消える**: もとの SPEC の簡潔さは犠牲になるが、実装と整合するほうを優先する。
- **窓ごとの目的記述が増える**: SPEC §3 が長くなる。ただし読みやすさは同 §3 line 59-60 の既存記法 (`#115 / ADR-0037` / `#125`) と揃うので追加負荷は小さい。

## 想定される影響

- **覆すコスト (低)**: SPEC 数行と本 ADR のみ。コード変更なし (#125 で既に実装済み)。窓ごとの値を変えたい場合は実装側の定数 (`TODAY_RECENT_WINDOW_DAYS=7` 等) を触るだけで、本 ADR を覆す必要はない。
- **Phase 2 トリガー**: 「Today カードに 7/14/31 切替を足したい」が出てきたとき、本 ADR §決定 3 の境界線 (= 同じ目的に複数窓は持たない) を再議論する必要がある。そのとき本 ADR を supersede するか、別目的 (= 別軸) として正当化するかの判断。
- **新規開発者向けの読み筋**: SPEC §3 単体読みで「窓は目的ごと」が見えるため、新たな窓を足したくなった実装者は自然にここを参照する。
