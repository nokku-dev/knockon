# 完成判定を Phase 1（Today 実機実使用）に前倒しし、v1 スコープを絞る

> **追記 (2026-08-15) — 前提の一部が実測で覆った。本文は当時の記録としてそのまま残す。**
>
> 本 ADR は「メトリクス手入力は、既に外部の個人記録用 DB で同種データを記録しているため二重記録になる（ANT 違反）」
> という前提で v1 スコープを絞った。その後の経過:
>
> 1. [ADR-0024](0024-goal-view-analytics-phase-3-unified.md) で「連携は read-only」を条件にメトリクスを v1 範囲へ取り込んだ。
> 2. しかし [ADR-0052](0052-remove-notion-metrics-integration.md) で、**その連携は実装されたが実際には使われていなかった**ことが
>    出荷前の確認で判明し、コードごと撤去した。
> 3. さらに参照先だった外部サービス自体を、組織側の判断（**nokku-ops ADR-0053**）で retire した。
>
> つまり「外部の個人記録用 DB があるから二重記録になる」という**前提そのものが消えた**。
> 本 ADR の結論（完成ゲートをコア体験＝ Today の実機実使用に置く）は維持されており、
> 覆ったのは ANT 違反の根拠に使った前提の側である。[K-004](../../KNOWLEDGE.md) / [K-005](../../KNOWLEDGE.md)（逆参照を残す運用）に従い、
> 本文を書き換えずにこの注記で示す。

## 文脈

旧 SPEC v0.3 / PLAN は完成判定（N=1 充足）を **Phase 4 終了時点 = 目標ビュー（メトリクス手入力）で実運用がアプリ上に閉じた状態** と定義していた。これを独立レビュー視点で見直すと 2 つの構造的問題が出てきた:

1. **ANT 違反**: 目標ビューは「メトリクスをアプリに手入力する」運用を要求する。自分は既に Notion Body Metrics と `/fitness` 経路で同種データを記録しており、目標ビューは **二重記録** を強制する。これは [CLAUDE.md](../../CLAUDE.md) §「Augmentation原則」の「ユーザーに行動変容を要求しない / 既存のフローに乗せる」に直接違反する。**完成ゲート自体が原則違反機能の上に乗っている** という状態だった（この失敗パターンは [KNOWLEDGE.md](../../KNOWLEDGE.md) K-004 として言語化済み）。
2. **完成基準がコアからずれている**: 本プロダクトのコア体験は「If-Then 連鎖を毎日 Today で記録し続けられる」こと。メトリクスはコアから 1 段外れた付随機能で、ここで完成を測ると **コア体験の良し悪し（毎日使えるか / 摩擦が許容範囲か）** を測れない。測りやすい代理機能を完成ゲートに据えてしまっていた。

加えて [KNOWLEDGE.md](../../KNOWLEDGE.md) K-001（設計精度が拘束条件を下げないなら消耗）/ K-003（コアモデルが固まる前の UI 精密化）の構造的な再発防止として、**実機到達 → 自分で数日使う** を最上位の検証ゲートに置き、それまで設計の精密化や付随機能の作り込みを禁止する必要があった。

[SPEC.md](../../SPEC.md) §1 で明示した既知の弱点（アナログで既に機能している自分の If-Then 運用に対し、デジタル版が低摩擦である保証はない）も、完成判定を実機実使用に置けば直接検証できる。

## 検討した選択肢

- **案A（採用）**: 完成判定を **Phase 1（Today が実機で動き、自分が数日継続して実運用を回せている）** に前倒しする。同時に **目標ビュー / メトリクス / サブチェーン参照（再帰1段）+ 白抜き星 / ウィンドウ 7・31 切替** を v1 非スコープに降格する（v1 は 14D 固定 / アクションノードのみ / 目標ビュー無し）。
- **案B（却下）**: 旧定義（Phase 4 完成）を維持する。
- **案C（却下）**: 完成判定を **Phase 2 または Phase 3**（編集 / 詳細）に置く。
- **案D（却下）**: 完成判定だけ Phase 1 に移し、目標ビューは v1 スコープに残す。

## 決定

案A を採用する。具体的に以下を固定する:

> **用語の分離**: 本 ADR では「**N=1 完成判定**」と「**v1 出荷スコープ**」を別概念として扱う。
> - **N=1 完成判定** = 自分の実運用がデジタル化されたと判断するゲート = **Phase 1 で測る**（実機で数日継続して回ること）。
> - **v1 出荷スコープ** = ストア提出までに実装する範囲 = **Phase 0〜3**（編集 / 詳細を含む）。
>
> つまり「Phase 1 で完成判定が立つ」と「Phase 2/3 もやる」は矛盾しない。Phase 1 で前提検証（毎日使えるか）が通った上で、Phase 2/3 は実使用で判明する不便を解消するために実装する。

1. **N=1 完成判定 = Phase 1（Today が実機で動き、自分のチェーンを載せて数日継続して回せている）**。
2. **早期検証ゲート（最上位ルール）**: Phase 1 が実機で動き自分が数日使うまで、サブチェーン / 目標ビュー / ウィンドウ切替 / 有料 / 同期などの **追加設計を一切進めない**。設計の精密化は前進ではなく消耗（K-001 / K-003）。本 ADR の他のどの判断より優先する。
3. **v1 非スコープへの降格**: 以下は出荷後レイヤー（実機実使用の後に要否判断）。
   - サブチェーン参照（再帰1段）+ それに付随する白抜き星表現
   - 目標ビュー / メトリクス（既存 Notion Body Metrics・/fitness と二重記録 = ANT 違反のため、連携前提が立つまで持たない）
   - ウィンドウ 7 / 31 切替（v1 は 14D 固定）
4. **維持する原則**: [ADR-0001](./0001-chain-data-model.md) のデータモデル原則（ノード = アクション or サブチェーン参照、再帰 1 段）は **維持**。v1 実装でアクションのみに絞るだけで、データ正準が `(ノード, 日付, bool)` のままなのでサブチェーンは後から **無移行で追加可能**。これが本 ADR を後から覆しても実装マイグレーションを発生させない構造的リターン。
5. [ADR-0002](./0002-loose-chain-judgement.md) ゆるい連鎖判定、[ADR-0003](./0003-firing-logic.md) 発火ロジック、[ADR-0004](./0004-design-direction-v02.md) デザイン方針はそのまま維持する。サブチェーン非スコープ化に伴う白抜き星廃止は ADR-0004 の核（モダンミニマル / 1 本スパイン / Celebrate 主 / 禁止 UI）と矛盾せず、付随変更として扱う。
6. **これは v1 の確定事項である**。早期検証ゲート（§決定2）は本 ADR の他のどの判断より優先する最上位ルールで、Phase 1 実機実使用が立つ前に「やはり目標ビューを v1 に戻す」「サブチェーンを v1 で実装する」などの再検討は **行わない**。再検討する場合は本 ADR を `superseded` にする新規 ADR が必要。
7. **派生 ADR**: チェーン / アクション CRUD は [ADR-0014](./0014-crud-phase-1-7-1-8-frontload.md) で Phase 2 から Phase 1.7-1.8 に前倒し。これは早期検証ゲートを破る判断ではなく、N=1 ユーザーが「編集・削除が必要なのは自明」と予測判断したことによる着手順序の変更。本 ADR の完成判定 (Today 実運用ループ数日継続) は維持される。

## 理由

- **ANT 原則との整合（最重要）**: 旧 Phase 4 完成判定は二重記録という行動変容をユーザー（自分）に強制し、Augmentation 原則に違反していた。完成ゲートが原則違反機能の上に乗る状態は、プロダクトの核を自分で踏みつけているのと同じ。Phase 1 完成判定はコア体験（毎日 Today で記録）そのものを測るので、追加の行動変容を要求しない。
- **コア体験ループの閉じる地点で測る**: 案C（Phase 2 / 3 を完成判定にする）は「編集できる / 詳細を見られる」を測れるが、**毎日使うかどうか**は測れない。コア体験は「Today で記録するループ」で閉じるので、ここを測らないと完成の意味が薄い。
- **prime objective との直接整合**: 「自分が毎日使う 1 本を最短で完成・出荷する」（[CLAUDE.md](../../CLAUDE.md)、[SPEC.md](../../SPEC.md)）の prime objective は **「使う」が中核**。「使えるアプリ」を完成判定に置くのが文字通りの整合。
- **設計の精密化を構造的に止める**: K-001 / K-003 の再発防止として、Phase 1 実機到達を最上位ゲートに置けば、それまで「あると良い機能」「精密な設計」が時間を食う構造を切れる。設計の手数を「使ってから不便だと判明したもの」だけに絞れる。
- **案D を却下する理由**: 完成判定だけ前倒ししても、目標ビューが v1 スコープに残ると ANT 違反機能が残り、結局そこに引っ張られて実装が膨らむ。完成判定の移動と非スコープ化はセットでないと意味が薄い。
- **後で覆すときのコストが低い設計を選んでいる**: [ADR-0001](./0001-chain-data-model.md) で「保存は事実、解釈は関数」を貫いた結果、サブチェーン / 目標ビュー / 追加ウィンドウは **データマイグレーションなしで後から足せる**。これにより「v1 から外す」判断のリバーシビリティが構造的に確保されている。0001 のデータモデル選択が本 ADR を取れる根拠そのもの。

トレードオフ:
- 「全機能が揃っていない v1」を出荷することになる（目標ビューや弱い輪の振り返り機能なし）。これは Phase 1 実使用で要否を判断するための意図的な穴で、機能完成度より実機到達速度を優先する判断。
- 「デジタル版がアナログ運用より低摩擦か」という SPEC §1 既知の弱点を Phase 1 で検証する。回らない場合は **設計ではなく前提（デジタル化の必要性）を疑う** 必要があり、その場合は本 ADR よりさらに上流の方針変更（プロジェクト継続自体の再考）が走る。

## 想定される影響

- **同 PR で同期更新が必要**: [SPEC.md](../../SPEC.md)（§0 完成判定追加、§2 v1 アクションのみ、§3 目標ビュー削除、§5 非スコープ拡大）、[PLAN.md](../../PLAN.md)（早期検証ゲート最上位、Phase 1 を完成判定の場と明記、Phase 4 削除）、[KNOWLEDGE.md](../../KNOWLEDGE.md)（K-004 追加）、[CLAUDE.md](../../CLAUDE.md)（プロジェクト固有の注意点 §2 / §5 文言）。本 ADR と矛盾するこれらの記述が残ると、後から読む人（自分含む）が混乱する。
- **既存 ADR との関係**: [ADR-0001](./0001-chain-data-model.md) のデータモデル原則は維持（supersede しない）。[ADR-0004](./0004-design-direction-v02.md) の白抜き星言及はサブチェーン非スコープ化で実質無効になるが、デザイン方針の核は維持されるため supersede しない（DESIGN-SYSTEM 側に「サブチェーン展開・白抜き星は v1 非スコープに伴い実装対象外」と残置するだけ）。
- **後で覆すコスト**: 「やはり目標ビューが必要 / サブチェーンが必要」と判断する場合、本 ADR を `superseded` にする新規 ADR が必要。データ層は無移行で足せる（0001 のリターン）ため、実装的なマイグレーションは発生しない。覆すコストは判断系譜の更新と UI 実装のみ。
- **PLAN への波及**: PLAN の Phase 4 / Phase 5 は v1 から消える（後から再追加する場合は新規 Phase として PLAN を更新）。Phase 0 / 1 / 2 / 3 のみが v1 のスコープ。
- **検証の意味づけ**: Phase 1 で自分が数日継続して使えれば v1 出荷判断可。使えない場合、デジタル化の前提自体を再検討する位置付け（設計の手戻りではなくプロジェクト方針の再考）。
