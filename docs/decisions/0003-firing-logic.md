# 発火ロジックは OS 標準ジオフェンス + 手動発火フォールバック / 有料地図 API は使わない

## 文脈

knockon は If-Then / habit stacking の連鎖を「起点アンカー」から始める設計で、起点アンカーは時刻 / 場所 / 行動のいずれかを取りうる（[SPEC.md](../../SPEC.md) §2、[0001](./0001-chain-data-model.md)）。このうち **場所発火** をどう実装するかが、外部依存・課金リスク・実装複雑度を大きく左右する。場所発火の選択肢は技術的に幅があり（OS 標準ジオフェンス / 有料 Places・地図 API / 自前のバックグラウンド位置監視）、選んだ手段はそのまま外部依存の輪郭になる。

同時に、自動発火（時刻 / 場所 / 行動アンカー）はどれも環境要因で **発火しない場面** が必ず存在する（位置権限が Always でない、ジオフェンス登録数上限超過、時刻通知の遅延、OS のサイレンス）。自動発火が落ちた瞬間に「今日その連鎖は出てこない」となると、Augmentation 原則（[CLAUDE.md](../../CLAUDE.md)）に反して **ユーザー側に「自動発火を正確に設定する責任」を押しつける** ことになる。

prime objective は「自分が毎日使う 1 本を最短で完成・出荷する」（[CLAUDE.md](../../CLAUDE.md)、[SPEC.md](../../SPEC.md) 冒頭）。v1 のクリティカルパスから外部依存と課金リスクを取り除き、最悪でも手動で連鎖が成立する土台を先に置く必要がある。実装に入る前に、場所発火の手段と手動発火の位置付けを ADR として固定する。

## 検討した選択肢

- **案A（採用）**: 場所発火は **OS 標準ジオフェンス**（iOS Core Location / Android Location）のみ。場所登録は v1 では **現在地登録のみ**（地図検索は後発スコープ）。**手動発火を v1 必須** とし、行動アンカー成立の中核に据える。ジオフェンス登録数上限はキューイングで吸収、位置情報 Always 拒否時は手動発火にフォールバック。
- **案B（却下）**: 従量課金の地図 / Places API（Google Maps Platform、Mapbox 等）を常設し、場所の検索登録と発火判定の両方に使う。
- **案C（却下）**: OS 標準ジオフェンスは使わず、アプリ独自のバックグラウンド位置監視を実装する。

## 決定

案A を採用する。具体的には以下を固定する:

1. **場所発火は OS 標準ジオフェンス専用**。iOS は Core Location の region monitoring、Android は Location の Geofencing API を使う。外部の地図 / Places API はクリティカルパスに含めない。
2. **場所登録は v1 では現在地登録のみ**。地図上での検索・任意地点登録は v1 非スコープ（後発フェーズ）。
3. **手動発火は v1 必須機能**。自動発火が効くかどうかに関わらず、ユーザーは任意のタイミングでチェーンを発火できる。手動発火を「行動アンカー成立の中核」として位置付け、自動発火はその上に乗る最適化レイヤーとして扱う。
4. **ジオフェンス登録数上限はキューイングで対応**。iOS の region monitoring 20 件などの OS 側上限を超えるチェーンが登録された場合、優先度（直近の利用頻度等）に基づいて入れ替える派生ロジックを持つ。上限超過はユーザーに失敗として見せない。
5. **位置情報 Always 拒否時は手動発火にフォールバック**。権限ダイアログで Always を取れなくても、アプリは劣化動作で機能する（手動発火で必ず成立する）。Always を要求する強制ダイアログ・繰り返しの再要求は出さない。
6. これは v1 の確定事項である。再検討する場合は本 ADR を `superseded` にする新規 ADR が必要。

## 理由

- **外部依存と課金リスクの排除**: 案B の有料 API は、ユーザー増加とともに従量課金が線形に膨らみ、prime objective（毎日使う 1 本を最短で出荷する N=1 プロダクト）に対して請求リスクが過大。さらに API 仕様変更・キー漏洩・障害がそのままアプリの場所発火の停止に直結する。v1 クリティカルパスからは外部依存を構造的に排除する。
- **OS 標準ジオフェンスで十分**: 場所発火の本質は「特定地点に入った / 出た」の検出であり、ジオフェンス API が直接提供する。地図表示・住所検索・POI データベースは v1 の発火に必要ない。場所登録を「現在地登録のみ」に絞れば、地図 UI そのものも不要になる。
- **手動発火を中核に置くことが Augmentation 原則**: 自動発火を主にすると、ユーザーは「自動発火が効くように環境を整える責任」（Always 権限を許可する、ジオフェンス精度を理解する、通知設定を最適化する）を負う。これは「ユーザーに行動変容を要求しない」という核（[CLAUDE.md](../../CLAUDE.md)、[SPEC.md](../../SPEC.md) §1）に反する。手動発火を必須かつ中核に置けば、自動発火は **あれば便利な最適化** に降格でき、システム側が認知負荷を吸収する構造になる。
- **案C を却下する理由**: 自前のバックグラウンド位置監視は OS の省電力ポリシーと戦い続ける実装になり、保守コストが恒常的に発生する。OS 標準ジオフェンスは OS 側で省電力最適化されており、登録さえすれば後はプラットフォーム任せにできる。v1 規模では自前監視の精度向上で得られるメリットより、保守コストの方が圧倒的に大きい。

トレードオフ:
- 場所登録が現在地のみになるため、まだ訪れたことがない場所（例: 来週行く新しいジム）を事前に登録できない。これは v1 では受け入れる（地図検索は後発スコープで追加可能、データモデルへの影響なし）。
- ジオフェンス登録数上限のキューイングは派生ロジックを 1 つ増やす。ただしユーザーから見える失敗を消す効果が大きいので採用する。
- 手動発火が必須機能になることで、UI 側に「発火ボタン」相当の動線を常設する必要がある（[DESIGN-SYSTEM.md](../../DESIGN-SYSTEM.md) 側で設計）。

## 想定される影響

- **実装スコープ**: v1 では地図 SDK・Places API クライアント・住所検索 UI を **入れない**。これらが PR に出てきたら本 ADR と矛盾するので弾く。位置情報レイヤーは OS 標準 API の薄いラッパー 1 層に閉じる。
- **権限フロー**: 位置情報の権限ダイアログは Always を 1 回だけ要求する穏当な実装にする。拒否されてもアプリは手動発火で成立するため、再要求ループや「Always にしてください」のモーダルは出さない。
- **発火ロジックの構造**: 「今日出すノード」を計算する関数は `起点アンカー判定 ∪ 手動発火履歴` の和集合で実装する。手動発火がない（= 自動発火のみが効いている）状態も、自動発火がない（= 手動発火のみで動いている）状態も、同じデータパスで等価に扱う。
- **後で覆すコスト**: 地図 / Places API を後から追加するのはデータモデルに影響しない（場所アンカーの座標フィールドはそのまま使える）。覆すのは「v1 で外部依存を持たない」という外部仕様の判断側で、コードよりも判断系譜の更新コストが主。
- **関連する back-fill**: 命名 knockon は [0005](./0005-product-name-knockon.md)、デザイン方針転換 v0→v0.2 と弱い輪の v1 廃止は [0004](./0004-design-direction-v02.md) に独立 ADR として back-fill 済み。
- **追記 ([ADR-0020](./0020-deprecate-manual-firing-concept.md))**: 「手動発火」ワードは [ADR-0020](./0020-deprecate-manual-firing-concept.md) で廃止された。 本 ADR §決定 第 3 項「手動発火は v1 必須」は意味的に維持されるが、 「Today に並ぶ active チェーン全表示 + ノードタップ」という日常フローと再定義 (K-015 同型の軸別再解釈)。 ADR-0003 本体の発火ロジック (場所/時刻 + 有料 API 禁止 + 等価データパス) はそのまま load-bearing。
