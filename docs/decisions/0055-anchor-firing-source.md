# アンカー発火に「どちらの経路で観測したか」を記録する（`anchor_firings.source`）

## 文脈

#301（Phase 1.6b）で OS ジオフェンス（region monitoring）を実装した結果、**アンカー発火を書き込む経路が 2 つ**になった。

| 経路 | 実装 | 通知 |
|---|---|---|
| 前景判定 | `useTodayData.detectPlaceFiringByGps`（Today の focus 復帰時に GPS で距離判定） | **出さない** |
| ジオフェンス | `geofencing.handlePlaceArrival`（OS の region Enter） | **出す** |

両者は同じ `(anchor_id, date)` を書き、[ADR-0012](./0012-anchor-firing-events.md) の「1 日 1 回の不可逆事実」で先に書いた方が勝つ。これ自体は正しい挙動で、アプリを開いたまま到着したときに通知が冗長にならない効果もある。

問題は **記録に経路が残らないこと**。`anchor_firings` は `(anchor_id, date)` だけなので、後から「この発火はどちらが観測したのか」を判定できない。

これは仮定ではなく、2026-08-16 の Simulator QA で**実際に 2 回詰まっている**:

1. 「範囲内 発火中」ピルが出ていたことを根拠に「前景判定が勝った」と判定したが、**誤診**だった。ピルを描く `anchorFiredToday` は `loadChainForToday` が DB を読んだ結果で、「読み込み時点で発火行がある」ことしか意味しない
2. 通知が出なかった事例で、(a) 前景判定が先に書いた のか (b) ジオフェンスが書いて通知したがバナーを見逃した のか **判定できなかった**

実運用でも同じことが起きる。「最近ジオフェンスの通知が来ない」と感じたとき、ジオフェンスが壊れているのか、単に前景判定が先に書いているだけなのかを区別する手段がない。**Phase 1.6b が実際に機能しているかを測る手段が無い**、とも言える。

## 検討した選択肢

- **案A（採用）**: `anchor_firings` に `source TEXT` 列を足す（`'foreground'` / `'geofence'`）。同じ行に、その発火を**どちらが観測したか**を持つ。
- **案B（却下）**: 別テーブルに診断ログを持つ。同じ事実について 2 つの真実源ができ、片方だけ消える / ずれる余地を作る。発火が 1 日 1 回である以上、同じ行に持てるものをわざわざ分ける理由がない。
- **案C（却下）**: PostHog にイベントを送る。[ADR-0053](./0053-analytics-platform-posthog.md) の 7 イベントに無い新規イベントになり、分析契約を広げる。加えて **手元での診断に使えない** — このリポジトリの QA 慣行は「DB 直読みが最も費用対効果が高い」（[ios-simulator-qa.md](../release/ios-simulator-qa.md)）で、実際 #273 の UTC 保存もそれで発見している。
- **案D（却下）**: 何も保存せず、dev ビルドのログでだけ区別する。今回困ったのは**後から**の判定であって、その場のログでは間に合わない。出荷ビルドで起きたことは追えない。

## 決定

案A を採用する。

1. **`anchor_firings` に `source TEXT NOT NULL` を追加**する。値は `'foreground'` | `'geofence'` の 2 値で `CHECK` 制約を付ける。
2. **[ADR-0012](./0012-anchor-firing-events.md) §決定1 のカラム定義を拡張する**（`anchor_id`, `date` → + `source`）。⚠ **ADR-0012 を supersede しない**: 同 ADR の核（アンカー発火は 1 日 1 回の不可逆な観測事実 / `PRIMARY KEY (anchor_id, date)` / 派生値は保存しない）は一切変えていない。変えるのは「その事実を**何が観測したか**」を同じ行に持つかどうかだけ。
3. **既存行の `source` は `'foreground'`** とする（migration の `DEFAULT`）。#301 以前はジオフェンス経路が存在しなかったので、過去の発火は全て前景判定によるもの。**推測ではなく事実**として確定できる。
4. **表示には使わない。** UI は `anchorFiredToday`（行の有無）だけを見る。`source` は診断と、Phase 1.6b が機能しているかの測定にのみ使う。

## 理由

- **経路は派生値ではなく観測事実**。「いつ発火したか」と同じく「何がそれを観測したか」も観測時にしか分からない情報で、後から履歴から導出できない。[ADR-0001](./0001-chain-data-model.md) の「派生値 / キャッシュ / 非正規化を保存しない」の対象ではない。むしろ [ADR-0012](./0012-anchor-firing-events.md) と同じく「保存は事実、解釈は関数」に沿う。
- **観測できないものは候補として思い付けない**。経路を持たないままだと、「ジオフェンスが実運用で効いているか」という問いに答えるデータが永久に手に入らない。Phase 1.6b を入れた判断が正しかったかを後から評価できない。
- **同じ行に持つのが最小**。発火は 1 日 1 回・1 行なので、経路も 1 行に属する属性。別テーブルにすると二重管理になる。
- **既存行を推測で埋めない**。`'foreground'` は「#301 以前にジオフェンス経路が存在しなかった」という事実からの確定であって、デフォルト値による埋め合わせではない。

## 想定される影響

- **スキーマ変更**: `SCHEMA_VERSION` 18 → 19、`MIGRATIONS[19]`。`ALTER TABLE ADD COLUMN` に `NOT NULL` を付けるには `DEFAULT` が必須（[K-034](../../KNOWLEDGE.md#k-034)）。
- **`recordAnchorFiring` のシグネチャが変わる**。呼び出し側 2 箇所（`useTodayData` / `geofencing`）が経路を渡す。⚠ 渡し忘れを型で止めるため、引数は省略可能にしない。
- **CLAUDE.md の「正準データは 5 軸」の記述**は変わらない（軸は増えず、既存の軸の属性が 1 つ増える）。
- **測れるようになること**: 発火のうちジオフェンス由来の割合。これが極端に低ければ、Phase 1.6b は実装されているが実際には効いていない、と判定できる。
- **測れないままのこと**: 「通知が配信されたか」までは分からない。`source='geofence'` は通知を**出そうとした**ところまでしか示さない（権限や OS 側の事情で出ないことはありうる）。
