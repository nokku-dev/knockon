# プロダクト名を `knockon` に確定する

## 文脈

If-Then / habit stacking 型の習慣アプリの user-facing なプロダクト名を確定する必要があった。差別化の核は **トリガー（直前の行為が次の起点になる）と連鎖（行動が積み上がる）** にあり、名前自体がその両方を含意できることが望ましい。

一方、習慣アプリは飽和カテゴリで、generic 名（"Habit Chain" 等）では ASO の head term を取れない構造になっている。発見性は **名前ではなくサブタイトル / キーワード欄** が担う前提で名前設計をする。

nokku 配下の既存プロダクト命名は「短く、小文字 ASCII、口語的」(`jotlog` / `tsundone.` / `Graft`) で揃っており、ここに整合させる必要もある。

本 ADR は back-fill: 命名は SPEC.md / CLAUDE.md / リポジトリ名で既に `knockon` に確定済みだが、判断の根拠が判断ログとして残っていなかったため、関連実装が増える前に記録する（[CLAUDE.md](../../CLAUDE.md) の「既出の基礎判断を back-fill する」指示に基づく）。

## 検討した選択肢

- **案A（採用）**: `knockon`。`knock`（入口 / トリガー感、konkon ＝ノックのモーション語彙とも一貫）に加え、英語の **"knock-on effect"（連鎖反応）** を含意として持つ造語的綴り。
- **案B（却下）**: 記述的な generic 名（例: "Habit Chain", "Chain Habit", "If-Then" 系）。
- **案C（却下）**: 素の `knock`。

## 決定

プロダクト名を **`knockon`** に確定する。

- リポジトリ名 / コード上の識別子 / nokku 配下の表示はすべて `knockon`（小文字 ASCII、ハイフン無し）。
- user-facing な文字列は 1 箇所に集約し、ハードコードしない（[CLAUDE.md](../../CLAUDE.md) §「プロジェクト固有の注意点」6 に既記載）。
- 発見性はサブタイトル / キーワード欄に "Habit Stacking" 等の head term を載せて担保する。名前自体に generic 検索性を負わせない。

## 理由

- **語に差別化が内包される**: `knock`（トリガー / 入口感）＋ `-on effect`（連鎖反応）で、トリガーと連鎖という本プロダクトの両軸が **一語で同時に立つ**。素の `knock`（案C）は入口感は出るが連鎖の含意が落ちる。
- **ASO 戦略との整合**: 飽和カテゴリで generic 名（案B）を取っても head term は埋もれる。記述名は短期 SEO に弱く、中長期では口コミ / 直接検索 / ブランド一貫性で劣化する。発見性はサブタイトル側に分離し、名前にはブランド資産を蓄積させる役割を担わせる。
- **nokku 命名規則との整合**: `jotlog` / `tsundone.` / `Graft` と同じ「短く小文字 ASCII / 口語的 / 造語性」のラインに乗る。配下プロダクト間の見た目の一貫性が、nokku というアンブレラの認知を支える。

トレードオフ:
- "knock-on effect" の英語ニュアンスは日本語話者にはストレートには通じない。これは説明文 / サブタイトル / オンボーディングで補う前提で許容する。
- 造語綴りのため、口頭での伝達時にスペルを聞き返される可能性がある。短さで相殺する想定。

## 想定される影響

- 影響範囲: リポジトリ名・パッケージ名・ストア掲載名・ドメイン・ロゴ・サブタイトル・キーワード欄すべてが本決定に従属する。後の出荷後フェーズで覆すと、ストア再申請・既存ユーザーの再認知コスト・SEO リセットが発生する（ストア掲載後は **事実上のロックイン**）。
- 出荷前フェーズで覆す場合: ストア前なので影響は限定的だが、本 ADR を `superseded` にし、新 ADR で `supersedes: [0005]` を記載する。
- 派生する未確定事項: サブタイトル / キーワード欄 / オンボーディングの英日コピー、ロゴのタイポグラフィ表記（`knockon` のレターケース / 句読点）。これらは別 ADR / DESIGN-SYSTEM 側で扱う。本 ADR では扱わない。
