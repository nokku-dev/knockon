# チェーンのデータモデルを「起点アンカー1つ＋ノード順序列」に確定し、正準データを `(ノード, 日付, bool)` のみにする

## 文脈

knockon は If-Then / habit stacking 型の習慣アプリで、差別化の核は「直前の行為が次の行為のトリガーになる連鎖」にある。この連鎖をデータとしてどう表現するかは、ビジネスロジック・UI・将来の拡張可能性すべての土台になる。

設計初期には「リンク = アンカー × アクション」というモデル（各リンクごとに固有のアンカーを持つ）と、達成記録をアクション単位で保存する選択肢があった。前者は「直前行為がトリガー」という habit stacking の本質に対して中間アンカーが冗長になる。後者は表示上の見え方（streak 系 UI）に引かれてデータ構造を歪めてしまい、文脈情報を不可逆に失うリスクがあった（[KNOWLEDGE.md](../../KNOWLEDGE.md) K-002 で言語化済み）。

実装に入る前にこのモデルを ADR として確定し、以後の派生フィールド追加・正規化崩しに対するハードガードレールにする。

## 検討した選択肢

- **案A（採用）**: チェーン = 起点アンカー 1 つ ＋ ノードの順序列。ノードは「アクション or サブチェーン参照」で、サブチェーン参照は再帰 1 段まで。中間アンカーは持たず、2 番目以降のノードのトリガーは「直前ノードの完了」として暗黙化（UI 非表示）。正準データは `(ノード, 日付, bool)` のみ。チェーン平均・連鎖の流れ・定着判定・星種別・進捗率はすべて表示時の派生関数で計算し、保存しない。
- **案B（却下）**: 旧「リンク = アンカー × アクション」モデル。各リンクが固有のアンカーを持ち、リンク単位で達成を記録する。
- **案C（却下）**: 達成をアクション単位（行為そのものの実行ログ）で保存し、チェーン文脈は派生で再構成する。streak 系プロダクトの一般的なモデル。

## 決定

案A を採用する。具体的には以下を不変条件として固定する:

1. チェーンモデルは **起点アンカー 1 つ ＋ ノード順序列**。中間アンカーは禁止。
2. ノードは **アクション or サブチェーン参照** の二択。サブチェーン参照の再帰は **1 段まで**。
3. サブチェーン達成（親視点）は内部のいずれか 1 ノードでも実行されれば達成扱い（ゆるい判定）。
4. 永続化される正準データは **`(ノード, 日付, bool)` のみ**。チェーン平均・連鎖の流れ・定着判定・星種別（円 / 塗り星 / 白抜き星）・進捗率は **保存しない / キャッシュしない / 非正規化カラムを足さない**。表示時に派生関数で計算する。

## 理由

- **habit stacking の本質との一致**: 「直前の行為が次のトリガー」という連鎖の意味は、起点アンカー＋順序列で必要十分。各リンクに固有アンカーを持たせる（案B）と、2 番目以降は「直前ノード完了」が暗黙のトリガーになるため、明示アンカーは冗長な装飾になる。データ構造の冗長は UI とロジック両方で増殖する。
- **可逆性で正準を選ぶ**: 案C のアクション単位保存は、表示上の見え方（streak）から引かれた選択だが、リンク（ノード）単位の文脈を **不可逆に失う**。ノード単位で保存すればアクション単位への集約は派生関数で復元できるが、逆は不可能。「保存は事実、解釈は関数」を貫くため、情報量が最大で可逆な方を正準にする（K-002 の教訓）。
- **派生値を保存しないことで差別化を守る**: 達成率・定着・星種別を保存すると、表示都合で正準データに引っ張られる修正が入り、If-Then の差別化がデータ層レベルで崩れる。派生関数に閉じ込めれば、表示ルールが変わってもスキーマは無傷で済む。

トレードオフ:
- 表示時に毎回派生計算が走るコストを許容する（v1 の N=1 規模では問題にならない想定）。
- 厳密 streak 系 UI（連鎖切れで後続をゼロ評価する見せ方）はこのモデル上では作れない。これは「ゆるい連鎖判定」の意図的な帰結であり、別 ADR で扱う。

## 想定される影響

- 実装側のハードガードレール: 派生値カラムの追加・キャッシュテーブル・非正規化はレビューで弾く。リポジトリ層は `(ノード, 日付, bool)` の書き込み / 読み出しのみを露出し、集約は domain 層の純粋関数として実装する。
- 後で覆すコスト: モデル変更は **データマイグレーション必須** で、永続化フォーマット・派生関数・UI 全層に波及する。覆すなら新規 ADR を作って本 ADR を `supersedes` に指定し、本 ADR の status を `superseded` にする。
- 関連する未 back-fill 判断: ゆるい連鎖判定（[SPEC.md](../../SPEC.md) §2「達成・連鎖判定」）、弱い輪の v1 廃止、デザイン方針転換 v0→v0.2、命名 knockon は別 ADR として独立に back-fill する。本 ADR では扱わない。
