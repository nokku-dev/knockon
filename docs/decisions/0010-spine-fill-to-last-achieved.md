# 線（スパイン）の意味を「連続実行範囲」から「達成済みノード範囲（fill-to-last-achieved）」に変更する

## 文脈

[DESIGN-SYSTEM.md](../../DESIGN-SYSTEM.md) v0.2 §4.1 と [SPEC.md](../../SPEC.md) v0.4 §2 で、スパイン（縦線）の意味を **「連続実行範囲」** と定めていた。

> 線は連続実行範囲（同一チェーン内で当日連続して達成されたノードの範囲）を表すが、その範囲外にあるノードも独立に点灯する。

これにより、たとえばノード 1 と 3 が達成・2 が未達の場合、線は「アンカー → 1」までで切れ、2-3 の間は `--line-bg`（暗いグレー）になる。3 のマーカー自体は独立に塗り潰し（ゆるい連鎖判定のため）になるが、線は繋がらない。

PR #13 (PLAN PR-1.3) で実装したスパイン描画を実機で初めて見たとき、この「飛ばすと線が切れる」挙動が **無意識のうちにペナルティ感を出してしまう** ことが分かった。具体的には:

- 達成済みドット同士が線で繋がらないため、「飛ばしたら線が分断された」という視覚的な後退印象が出る。
- [CLAUDE.md](../../CLAUDE.md) §Augmentation原則「マイナスを指差さない / 積み上がりと定着だけを可視化する（Celebrate 主）」と微妙にずれる。線の分断は意図せずマイナスを指差している。
- [ADR-0002](./0002-loose-chain-judgement.md) のゆるい連鎖判定（各ノード独立達成）とは「マーカー単位では独立」が成立するが、線（達成の流れの表現）は依然として連続性ペナルティを課している状態で、判定とビジュアルが一貫しない。

[DESIGN-SYSTEM.md](../../DESIGN-SYSTEM.md) は冒頭で「v0.2 / 変更前提」と明記しており、実機実使用での違和感を受けて変更するのは想定範囲内。むしろ早期検証ゲート（[ADR-0006](./0006-phase1-completion-and-scope-narrowing.md)）の精神そのもの。

## 検討した選択肢

- **案A（採用）**: スパインの意味を **「達成済みノード範囲」** に変更する。アンカーから「**最後に達成済みのノード**」まで `--grow`、それ以降は `--line-bg`。途中に未達ノードがあっても、両端が達成済みなら線は繋がる扱い。
- **案B（却下）**: 「連続実行範囲」を維持する（[ADR-0002](./0002-loose-chain-judgement.md) のゆるい判定との一貫性を犠牲にする）。
- **案C（却下）**: 達成済みノード間の各セグメントを個別評価する（例: 1→2 は 1 が達成・2 が未達なので、1→中間まで `--grow`、中間→2 まで `--line-bg`、2→3 まで …）。判定が複雑で、ユーザーから見て予測しにくくなる。

## 決定

案A を採用する。具体的に以下を固定する:

1. **スパインの `--grow` 範囲 = アンカー → 最後に達成済みのノード**。途中に未達ノードがあっても線は繋がる扱い。
2. **最後に達成済みのノード以降は `--line-bg`**。全ノード未達の場合はスパイン全域が `--line-bg`（アンカードットのみ `--grow`）。
3. **マーカー自体の状態は変えない**: 達成済みは `--grow` 塗り、未達は白抜き円。**ゆるい連鎖判定（各ノード独立）は維持**。
4. **派生関数を `firstUnachievedNodeIndex` から `lastAchievedNodeIndex` に置き換える**（[src/domain.ts](../../src/domain.ts)）。前者は本 ADR と矛盾するため削除する。
5. 同 PR で [DESIGN-SYSTEM.md](../../DESIGN-SYSTEM.md) §4.1 と [SPEC.md](../../SPEC.md) §2 を更新（K-005: 仕様書を実装と同期させる）。
6. これは Phase 1.3 確定事項。覆す場合は本 ADR を `superseded` にする新規 ADR が必要。

## 理由

- **Augmentation 原則との整合性が高まる**: [CLAUDE.md](../../CLAUDE.md) §Augmentation原則 / [DESIGN-SYSTEM.md](../../DESIGN-SYSTEM.md) §0 で「マイナスを指差さない / Celebrate 主」を掲げている。「飛ばしたら線が切れる」は意図せずマイナスを指差すビジュアルだった。「達成済み同士は繋がる」方が達成感を強化する。
- **ゆるい連鎖判定とビジュアルの一貫性**: [ADR-0002](./0002-loose-chain-judgement.md) で「ノード達成は独立、後続をゼロ評価しない」と決めている。線が「連続実行範囲」を表すと、判定（独立）とビジュアル（連続）が一貫せず、ユーザーは「結局飛ばしてはダメなのか?」という疑問を抱く。「達成済みノード範囲」なら判定とビジュアルが揃う。
- **早期検証ゲートの正規ルート**: [ADR-0006](./0006-phase1-completion-and-scope-narrowing.md) の早期検証ゲート（実機で触らないと違和感は出ない）の精神そのもの。Phase 1.3 で実機を見て初めて違和感が顕在化したので、設計を精密化する前に変更を入れる。[K-003](../../KNOWLEDGE.md) の「UI はモデル検証の道具として安く回す」とも整合。
- **データ層に影響なし**: 線の意味は派生表示の話で、正準データ `(node_id, date, achieved)` の構造は変わらない。[ADR-0001](./0001-chain-data-model.md) の「保存は事実、解釈は関数」原則のリターン。
- **案B を却下する理由**: 「連続実行範囲」は habit stacking 教科書通りの厳密モデルへ寄せた解釈で、本プロダクトの設計思想（ゆるい / Celebrate 主）とそもそも整合していなかった。実装してみて初めて気付いた。
- **案C を却下する理由**: セグメント単位の評価は予測しにくく、UI 説明の負担が大きい。「達成済み同士は繋がる」のシンプルな意味づけが説明にも実装にも優しい。

トレードオフ:
- DESIGN-SYSTEM v0.2 §4.1 の「線は連続実行範囲」記述を覆すことになる（v0.2 は「変更前提」と明記済みなので supersede ではなく改訂扱い）。
- 「線がどこまで伸びるか」を見ても、その日の **連続成功** が分からなくなる（達成密度しか見えない）。これは Phase 1 規模では受容可能。連続性を視覚化したい需要が出てきたら別表現（例: マーカー間の小さなチェックマーク）で追加検討。

## 想定される影響

- **同 PR で同期更新が必要 (K-005 / spec-sync.md)**:
  - [SPEC.md](../../SPEC.md) §2「達成・連鎖判定」の「線（スパイン）の表示意味」記述を更新
  - [DESIGN-SYSTEM.md](../../DESIGN-SYSTEM.md) §4.1「スパイン（チェーン）」の説明を更新
  - [ADR-0009](./0009-react-native-svg-for-spine.md) §決定3 で言及される派生関数名（`firstUnachievedNodeIndex`）を `lastAchievedNodeIndex` に書き換える、または ADR-0009 に逆参照を残す（K-005 ルール: 影響を受ける ADR 側に逆参照を残す）。
- **コード変更**:
  - [src/domain.ts](../../src/domain.ts) の `firstUnachievedNodeIndex` を `lastAchievedNodeIndex` に置換（-1 = 全ノード未達、index ≥ 0 = 最後に達成済みのノードの位置）。
  - [src/TodayScreen.tsx](../../src/TodayScreen.tsx) の `filledEndY` 計算を新関数に切替。
  - [src/domain.test.ts](../../src/domain.test.ts) のテストを書き換え（飛ばし達成のケースで線が繋がるアサーション）。
- **既存 ADR との関係**: [ADR-0001](./0001-chain-data-model.md)（データモデル）/ [ADR-0002](./0002-loose-chain-judgement.md)（ゆるい連鎖判定）はそのまま維持（むしろ整合性が高まる）。[ADR-0009](./0009-react-native-svg-for-spine.md) は派生関数名の言及だけ古くなるので逆参照を入れる（supersede ではない / 描画手段の選定自体は無効化されない）。
- **後で覆すコスト**: 派生関数の差し替えだけで済む（[ADR-0001](./0001-chain-data-model.md) の「保存は事実、解釈は関数」のリターン）。データマイグレーションは不要。
- **これは Phase 1.3 の確定事項**。線の意味解釈について Phase 1 実機実使用後にさらに変更が必要になった場合（例: 連続性も可視化したい）は、本 ADR を `superseded` にする新規 ADR が必要。
