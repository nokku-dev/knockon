# 研究画面の手動メモ — `notes` データ軸の追加 (node_id 単一 nullable / ON DELETE SET NULL)

## 文脈

Issue #181 (Graft POST 01KVW1200H744PTEP41JE7SDG5): 研究タブ (#175 で空スケルトン追加済み)
に、 アプリによる自動検出 (インサイト) 以外に **ユーザーが自分でメモを書ける** ようにする。

導線は 2 つ:

1. **研究画面 右下 FAB** — 特定のチェーンおよびアクションを選択してからメモを記録できる
   (選択なし = 汎用メモも可)。
2. **Today のアクション長押し** — 長押しした対象のチェーンとアクションが自動選択された
   状態でメモを書ける。

設計判断ポイント (Issue 本文が「設計余地あり」と明示):

1. **メモとチェーン / アクションの紐付けデータモデル** — どの粒度・どの軸で持つか。
   これは CLAUDE.md §load-bearing #1 の「正準データは 3 軸」制約に新しい事実軸を足す判断。
2. **ノード削除時のメモの扱い** — メモを消すか残すか。
3. **手動メモと自動インサイトの研究画面上の表示統合方針**。

## 検討した選択肢

### 1. 紐付けデータモデル

- **案 A: `node_id` 単一 (nullable)** ← 採用
  - メモは「特定チェーン内の特定アクション位置 (= ノード)」に紐付く。汎用メモ = `node_id` NULL。
  - 正準データ `achievements` (`node_id` 基準) と粒度が一致する。最小カラム。
  - FAB の「チェーン → アクションを選択」は「チェーンでフィルタしてそのノードを選ぶ」に写像。
    Today 長押しは対象ノードを直接 `node_id` にセット。
  - 制約: 「チェーン横断の同一アクションへのメモ」は表現できない (= ノードは特定チェーン固有)。
    Phase 1 N=1 では問題にならない (= メモは「今このチェーンのこのアクションで気づいたこと」)。
- 案 B: `chain_id` + `action_id` 2 軸 (各 nullable) — POST 文言に最も忠実だが、`achievements`
  (node 粒度) と軸がずれ、「片方だけ選択」など状態が増える。チェーン横断アクションメモは表現できるが
  v1 では使い道がない。
- 案 C: 汎用 `target_kind` + `target_id` (polymorphic) — 将来インサイトにもメモ可だが、FK 型安全性を
  失い、現時点では過剰設計。

→ **案 A**。ユーザーと対話で確定 (Issue #181 pickup セッション)。正準データとの粒度一致と最小性を優先。
表示時に `node → action(label)` / `node → chain` を派生で引けるので「どのチェーンのどのアクション」は
保存せず派生表示できる (ADR-0001 「保存は事実・解釈は派生」と整合)。

### 2. ノード削除時のメモの扱い

- **`ON DELETE SET NULL`** ← 採用
  - ノード (またはチェーン経由 CASCADE) が消えても **メモ本文は残し**、`node_id` を NULL にする
    (= 汎用メモに格下げ)。
  - 理由: メモはユーザーが書いた事実。Augmentation 原則「ユーザーの記録を勝手に消さない」を優先。
  - トレードオフ: 紐付け文脈 (どのアクションのメモだったか) は失われ、研究画面では汎用メモとして残る。
    文脈が消えても本文を消すよりは穏当と判断。
- 案: `ON DELETE CASCADE` (メモもノードと一緒に消す) — データは綺麗だがユーザーの書いたものを
  消すため不採用。

### 3. 手動メモと自動インサイトの表示統合

- 現時点で **自動インサイト機能は未実装** (研究タブは空スケルトン)。
- 本 PR では研究画面は **手動メモ一覧 + FAB** のみ実装する。
- インサイトが実装されたら、研究画面で「メモ」と「インサイト」を別ソースとして併置表示する
  余地を残す (= `notes` テーブルはメモ専用に保ち、インサイトは別の派生 / 別テーブルで扱う)。
  notes に `source` 列を足してインサイトを混ぜることは **しない** (= メモは観測事実軸、
  インサイトは派生値軸で別物。ADR-0001 の「派生値を保存しない」と整合)。

## 決定

1. **`notes` テーブルを新設する。これは正準データの新しい「観測した事実」軸**
   (ADR-0012 `anchor_firings` / ADR-0024 `metrics` と同型、K-015 の「軸別に拡張」パターン)。
   CLAUDE.md §load-bearing #1 の「正準データは 3 軸」は **4 軸目: メモ
   `(note_id, node_id?, content, created_at, updated_at)`** に拡張される。メモは派生値ではなく
   ユーザーが書いた事実なので、この拡張は ADR-0001 の「派生値を保存しない」禁則には触れない。

   ```sql
   CREATE TABLE notes (
     id TEXT PRIMARY KEY,
     node_id TEXT REFERENCES nodes(id) ON DELETE SET NULL,  -- NULL = 汎用メモ
     content TEXT NOT NULL,
     created_at TEXT NOT NULL,  -- ISO-like (秒精度)
     updated_at TEXT NOT NULL
   );
   ```

2. 紐付けは **`node_id` 単一 (nullable)**。汎用メモは `node_id` NULL。
3. ノード削除時は **`ON DELETE SET NULL`** (メモ本文保全、紐付けのみ解除)。
4. 導線は研究画面 FAB (チェーン → アクション選択 or なし) + Today アクション長押し (node 自動選択)。
5. 研究画面は手動メモ一覧のみ。インサイトとの統合表示は機能実装時に別ソース併置で行い、
   notes にインサイトを混ぜない。

## 想定される影響

- **CLAUDE.md §load-bearing #1 の「正準データは 3 軸」記述を 4 軸 (メモ追加) に更新する**
  (K-015 / K-005: 影響を受ける既存記述に逆参照を残す)。ADR-0001 にも本 ADR への逆参照を 1 行残す。
- スキーマ不変条件テスト (K-006) に `notes` の列固定・`node_id` の `ON DELETE SET NULL`・
  テーブル一覧への追加を機械検証として組み込む。
- `SCHEMA_VERSION` を 13 → 14 に bump し `MIGRATIONS[14]` で既存ユーザーに ALTER ベースで追加
  (ADR-0027、データ保全)。`notes` は新規テーブル CREATE のみ (既存データへの ALTER なし)。
- SPEC §2 (データモデル) / §3 (研究ビュー) を同期更新する。
- 反 streak / Celebrate 主 (ADR-0036) との関係: メモはユーザーの自由記述で数字・グリフ・
  ハイライトを新規追加するものではないため、ADR-0036 §一般原則の「失われうるか (+/-)」判定軸の
  対象外。
- **削除導線 (Issue #200, K-005 逆参照)**: 本 ADR §決定 4 (導線) は「作成」の 2 経路のみを規定していた。
  Issue #200 で削除導線を **編集モーダル内の「このメモを削除」ボタン + `Alert.alert` 確認** に
  集約 (研究画面カード長押しでの削除ジェスチャは撤去)。 理由: 隠し長押しは発見性が無く、
  かつ Today アクション長押し (= メモ**作成**) と研究画面カード長押し (= メモ**削除**) の
  意味論分裂は Augmentation 原則「新しい記法・運用ルールの学習を強制しない」に反する。
  destructive トークンは PR-1.8a (DESIGN-SYSTEM §1) を再利用。
